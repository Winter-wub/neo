# Research: can a compiled Bun binary do everything the Neo daemon needs on macOS?

Ticket: `../issues/01-bun-compile-capabilities.md` · Date: 2026-10-25 · Bun tested: **1.4.2** (`~/.bun/bin/bun`), macOS 27 (Darwin 27.0.0), arm64.

## Method

- Read the current backend to see what it actually uses: `app/server.js` (`/api/audio` at ~L637, `/api/events` at ~L662, `runClaude` at L119, `listenOn`/`networks` at L776-L820), `app/providers.js` (ACP over stdio, L64-L78), `app/discover.js`, `app/pairing.js`, `app/neo-agents-mcp.js`, `app/mac/build.sh`, `app/mac/Sources/Core.swift`.
- Built throwaway experiments with `bun build --compile` in `<scratchpad>/bunlab/` (`main.ts`, `pg.ts`, `hot.ts`, `t2.sh`, `feeder.py`, `fake-claude.sh`, `T.app`). Used ports 1873x/1874x only. Never ran the real `claude` (used `fake-claude.sh` instead).
- Primary sources: Bun docs and GitHub, Apple developer docs (via the JSON doc API), `man launchd.plist`, and Apple DTS (Quinn) posts on the Developer Forums.

Something the inventory turned up: there is no `app/apple-stt` folder. Apple STT now runs **inside the Swift app** (`SpeechService` in `app/mac/Sources/Core.swift` serves `127.0.0.1:8001/stt`), and `server.js` calls it over HTTP (`appleSTT`, L262). The daemon only needs to be an HTTP client of it. The part that matters for this ticket is where SFSpeechRecognizer can run (row 12), and ticket 08 covers that.

## Capability table

Legend: **works** · **caveat** = works with caveat · **doesn't** · **unverified**

| # | Need (what the current code does) | Verdict | Evidence |
|---|---|---|---|
| 1 | Long-lived HTTP server, streamed **chunked request body** (`/api/audio`: PCM s16le, 3200 B every 100 ms, open for minutes) | **works** | Experiment: chunked upload from Python `http.client` with `encode_chunked=True`. **node:http** (`req.on('data')`) and **Bun.serve** (`for await (const c of req.body)`) both got 29 chunks of 3200 B, each arriving about 100 ms after the last (streamed incrementally, not buffered), and each replied at the end. |
| 2 | Upload with a gap (phone hiccup) longer than 10 s | **caveat** | Experiment: 12 s pause mid-upload. Both survived: node:http with `requestTimeout = 0`, and Bun.serve with `server.timeout(req, 0)`. The catch: Bun.serve's **default `idleTimeout` is 10 s, max 255, and 0 disables it**; `server.timeout(req, 0)` does the same per request ([Bun docs: HTTP server](https://bun.com/docs/runtime/http/server)). Leave that out and the stream gets cut. |
| 3 | Long-lived **NDJSON streaming response** (`/api/events`, ping every 15 s) | **caveat** | Experiment, ping interval 12 s, 30 s client: **Bun.serve with the default idleTimeout closed the stream at about 12 s** (1 line received). Bun.serve with `server.timeout(req, 0)` stayed open for 30 s (3 lines). node:http (`res.write` + `requestTimeout = 0`) stayed open for 30 s (3 lines). The rule is the same as row 2: disable the idle timeout per streaming request, or keep pings under 10 s. |
| 4 | Detect a client disconnect on the event stream (drop the listener, clear the keepalive) | **works** | Experiment: Bun.serve fires both `req.signal` `abort` and `ReadableStream.cancel()`. node:http fires `req.on('close')`. All were seen when curl hit `--max-time`. |
| 5 | Spawn the `claude` CLI with streaming stdin/stdout (stream-json), then kill it on cancel or timeout | **works** | Experiment with `fake-claude.sh` from a compiled binary: `node:child_process.spawn` with piped stdio. Lines written to stdin came back as stdout lines in real time. `p.kill()` sent SIGTERM (the trap ran, exit 143). `spawn({signal})` + `AbortController.abort()` also gave SIGTERM. |
| 6 | Kill a whole agent tree (claude/ACP agents start their own children, such as MCP servers) | **works** | Experiment `pg.ts`: `spawn(..., {detached: true})` + `process.kill(-pid, 'SIGTERM')` killed both grandchildren (pgrep found 0 after). The current code only does `p.kill()`, which never reached grandchildren under Node either, so this is an improvement, not a parity requirement. |
| 7 | ACP agents over stdio JSON-RPC (`providers.js`), the `discover.js` probe (`initialize` handshake, 10 s timeout, kill) | **works** | Same mechanism as row 5 (line-delimited JSON over piped stdio). Experiment: the self-spawned JSON-RPC child replied to `initialize`. |
| 8 | `discover.js`: `execFileSync('npm', ['root','-g'])`, PATH scanning with `fs.accessSync/statSync/realpathSync`, reading the acpx registry from global `node_modules` | **caveat** | Experiment: `execFileSync('npm', …)` returned the fnm global root from the compiled binary. The caveat has nothing to do with Bun: **under launchd, PATH is the minimal system PATH**. Today `Core.swift` (`userPath`, L43) runs `zsh -lic` to get it and passes `PATH` to node. The daemon needs its own way to get it (for example, store the PATH captured by Neo Console during onboarding, or run the login shell itself). |
| 9 | `pairing.js`: `crypto.randomInt`, `randomBytes`, `createHash('sha256')`, `timingSafeEqual`, `fs.writeFileSync(..., {mode: 0o600})` | **works** | Experiment: `randomInt`, `sha256` and `timingSafeEqual` returned correct results in the compiled binary. `req.socket.remoteAddress` and the header checks are plain node:http and work the same way (node:http in Bun is built on `Bun.serve`, as the stack trace of the `EADDRINUSE` error showed: `node:_http_server … Bun.serve`). |
| 10 | LAN/Tailscale address discovery (`os.networkInterfaces()`, binding one extra server per IP, running `tailscale status --json`) | **works** | Experiment: it returned `en0=192.168.1.x` and `utun8=100.x.x.x` (the CGNAT/Tailscale address). Binding several `http.createServer` instances to specific IPs is the same API used in rows 1-3. **The code doesn't use mDNS/Bonjour at all** (nothing in `app/` mentions `bonjour`, `mdns` or `dns-sd`), so this needs nothing extra. |
| 11 | Run the MCP server over stdio from the same binary (`neo mcp`) | **caveat** | Experiment: the compiled `neo` spawned `process.execPath` with `['mcp']` and talked JSON-RPC over stdio. In a compiled binary, `process.execPath` is the binary itself, but **`process.argv` is `["bun", "/$bunfs/root/neo", ...userArgs]`**, so subcommands are read from `argv[2]` onward. The caveat: today `server.js` L73 writes `{command: process.execPath, args: [path to neo-agents-mcp.js]}` into the MCP config, and in NeoCli that becomes `{command: <absolute path of neo>, args: ["mcp"]}`. Use the real path inside the .app (or the PATH symlink), not `argv[0]`. |
| 12 | Apple Speech (SFSpeechRecognizer) from the daemon | **doesn't** (in the Bun binary) | Bun has no Objective-C or Swift bridge; `bun:ffi` is C ABI only, and Speech needs ObjC blocks and delegates. Even with a bridge, Apple says that without `NSSpeechRecognitionUsageDescription` in the Info.plist, "your app crashes when it calls `requestAuthorization(_:)`" ([NSSpeechRecognitionUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsspeechrecognitionusagedescription), [requestAuthorization](https://developer.apple.com/documentation/speech/sfspeechrecognizer/requestauthorization(_:))). A Bun binary has no bound Info.plist (`codesign -dv` shows `Info.plist=not bound`). STT therefore has to stay in Swift code that has its own Info.plist, which is ticket 08. |
| 13 | `.env` / `bunfig.toml` autoload in compiled binaries | **caveat** | Experiment: running the compiled binary from a directory that contains `.env` with `FOO=…` made `process.env.FOO` appear. Building with `--no-compile-autoload-dotenv --no-compile-autoload-bunfig` stopped it. The docs confirm: "`.env` and `bunfig.toml` loading is **enabled**" by default ([Bun docs: executables](https://bun.com/docs/bundler/executables)). If you skip the flags, `neo` run inside a user's project directory would pick up that project's `.env`. |
| 14 | Signing the compiled binary (hardened runtime) | **caveat** | Bun docs: "Codesign support requires Bun v1.2.4 or newer", and they recommend an `entitlements.plist` with `com.apple.security.cs.allow-jit` and friends ([Bun docs: executables](https://bun.com/docs/bundler/executables)). The older blocker ([oven-sh/bun#7208](https://github.com/oven-sh/bun/issues/7208), "main executable failed strict validation") was closed as completed on 2025-02-25 via PR #17207. Experiments: the output is already ad-hoc linker-signed with `Identifier=a.out`. Re-signing with `--options runtime --entitlements` passed `codesign --verify --strict`. **Without `allow-jit`, the hardened-runtime binary still runs but JIT is silently disabled: a hot loop took 8459 ms instead of 1099 ms (about 8x slower).** With only `allow-jit` it took 1012 ms. Always pass `-i <bundle-style id>` so the identity isn't `a.out`. |
| 15 | Nesting the binary inside the signed .app | **works** (as far as it can be tested locally) | Experiment `T.app`: signed `Contents/Helpers/neo` (hardened runtime + `allow-jit`, Apple Development identity), then signed the app. `codesign --verify --deep --strict` reported "valid on disk / satisfies its Designated Requirement", and the nested binary ran. Apple's guidance puts helper executables inside the bundle, for example `Contents/Resources` ([Updating helper executables](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos)). Sign inside-out and don't use `--deep` for signing. |
| 16 | Notarization | **unverified** | This machine only has an "Apple Development" identity (`security find-identity`), and notarization needs Developer ID Application + a secure timestamp. `spctl` rejected the test app as expected. Nothing found in primary sources reports Bun-specific notarization failures after 1.2.4. In #7208, the Electrobun author works around it by notarizing the .app that contains the Bun binary, which is the shape planned here. Confirm by running `notarytool` once with a Developer ID certificate. |
| 17 | Starting the daemon with launchd from inside the app (LaunchAgent) | **works** (documented) | `SMAppService.agent(plistName:)`: the plist must be in `Contents/Library/LaunchAgents`. Use `BundleProgram` (a path relative to the bundle) instead of `Program`. "LaunchAgents … in the app bundle automatically associate with that app in the Login Items panel" ([SMAppService.agent](https://developer.apple.com/documentation/servicemanagement/smappservice/agent(plistname:)), [Updating helper executables](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos), `man launchd.plist`: "BundleProgram … only supported for plists that are installed using SMAppService"). The current app already uses `SMAppService.mainApp` (SettingsView.swift L31). |
| 18 | TCC attribution (Full Disk Access, Files and Folders) when the daemon is started by launchd instead of by the .app | **unverified** (risk) | Apple DTS: "The algorithm used by TCC to track from a process to its responsible code is both undocumented and complex" and "TCC tracks access via code signing constructs, and those are properties of the *executable*" ([forum 760291](https://developer.apple.com/forums/thread/760291)). Responsibility "most often breaks when the child process does something 'odd'… such as trying to daemonise itself". If a launchd agent isn't attributed to the app, add `AssociatedBundleIdentifiers` ([forum 678819](https://developer.apple.com/forums/thread/678819)). `man launchd.plist` CAVEATS: "Daemons and agents managed by launchd are subject to macOS user privacy protections." **What changes:** today, `TimeViews.swift` L6 relies on "allow Neo.app once and it covers node/claude/agents" because node is a *child of Neo.app*. Under a LaunchAgent, the daemon has no app parent. Whether TCC charges prompts and grants to Neo Console (the bundle), or to the bare `neo` binary (no Info.plist, so the prompt has no usage string), wasn't tested: that would mean loading a LaunchAgent and triggering TCC on this Mac. Spawned `claude`/agents inherit whatever the daemon gets. |
| 19 | A stable TCC identity across rebuilds | **caveat** | This follows from row 18 plus Apple's statement that TCC keys on code signing: an ad-hoc signature (what `build.sh` uses today, `codesign -s -`) has no team, so its designated requirement is the cdhash. Every rebuild then looks like a new program, and grants such as Full Disk Access would reset. Sign with a real team identity and a fixed `-i` identifier. |
| 20 | Size / architecture | **caveat** | The compiled binary is about 62 MB (arm64 only). Bun's own docs say "Bun's binary is still way too big". That's acceptable, and similar to the bundled `node` it replaces. |

## Blockers that would force a different packaging choice

None of these force giving up on "one `bun build --compile` binary inside the signed .app". Two of them shape *how* it is packaged:

1. **Apple STT can't live in the Bun binary** (row 12). It has to stay Swift: either inside Neo Console (as now, which means STT only works while Console is running) or in a small Swift helper .app that the daemon talks to over HTTP. This belongs to ticket 08 and doesn't block NeoCli.
2. **TCC attribution under launchd is undocumented** (row 18). If testing shows that grants go to the bare `neo` binary instead of Neo Console, the fallback stays inside the same plan: wrap the daemon in a minimal nested bundle (for example `Contents/Helpers/Neo Daemon.app/Contents/MacOS/neo`) with its own Info.plist (usage strings, `CFBundleIdentifier`) and the same team ID, and point the SMAppService plist's `BundleProgram` at it. The *same* compiled binary can still serve as `neo` on PATH (via a symlink to it). Test this first with a Developer ID or Apple Development build: register the agent with SMAppService, touch `~/Documents` from the daemon, and see which name the prompt and System Settings show.

Must-do build settings (not blockers):

- Compile with `--no-compile-autoload-dotenv --no-compile-autoload-bunfig` (row 13).
- Sign with `--options runtime`, an entitlements file containing at least `com.apple.security.cs.allow-jit`, `-i com.mochi.neo.cli` (or similar), and a team identity (rows 14, 19).
- In Bun.serve, call `server.timeout(req, 0)` for `/api/audio` and `/api/events` (or set `idleTimeout: 0`). With node:http, keep `requestTimeout = 0` (rows 2, 3).
- Write the MCP config entry as `{command: <absolute neo path>, args: ["mcp"]}`, and parse subcommands from `process.argv.slice(2)` (row 11).
- The daemon has to work out the user's PATH itself, because launchd won't provide it (row 8).
- Not Bun-specific, but the move breaks it: `NEO_APP_TOKEN` is currently generated per run by Neo.app and passed to node through env (`Core.swift`). A daemon that runs on its own needs another way to share that secret with Console (ticket 05/06).
